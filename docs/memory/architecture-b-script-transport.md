# Architecture B — script transport without redundant ownership

Independent design for task `t_63d63bc7`, 2026-09-07. Recommendation, not implementation or performance acceptance. No sibling architecture report was read. Source inspected on `codex/memory-diagnostics`, initially HEAD `37ca48e`; `crates/script/src/load.rs` already had another worker's uncommitted capture-test seam. Line references below describe the inspected working source, not a claim that the dirty file is a frozen build input.

## Decision

Keep one isolate per started script and the maintained compatibility adapter. Make the bridge a **borrowed projection → exact delta → owned consumable packet → eager V8 materialization** pipeline. Remove temporary ownership on both sides and reuse at most two consumed packet allocations per isolate. Preserve the existing FIFO command grammar, publication edges, JS object construction and tick execution. Do not sell this as the architecture that closes the memory budget alone.

The concrete first discriminator is consumed-buffer reuse with the existing FlatBuffer encoding. Next, independently remove action-string projection clones and temporary reader vectors. These are finite changes at identified seams, not a new JS runtime. An aggressive second-stage retained-memory option is an exact compact family baseline that also supplies immutable transport payloads; it requires a private encoding decision and a net-owner proof before implementation. It is not a prerequisite for the first stage.

The distinction matters: copying fewer bytes is useful CPU work removal; keeping two large free buffers is not automatically a memory improvement. Similarly, replacing a fingerprint with a second full `GameSnapshot` or retaining historical snapshots can make memory worse.

### What is actually skipped

`script_observe` posts Snapshot then Tick at PLAYER_INFO edges while Running, including guardian hold. The nearby older doc comment saying held JS ticks are not dispatched is superseded by executable code at 698-755: held JS ticks still paint. This bridge does not publish at every 20ms logical client iteration.

Both directions use unbounded channels (`load.rs:1037-1038`). `on_game_tick:1119` folds completions, checks the previous dispatch against the existing 50ms slow threshold, arms termination if over budget, then sends Tick. This is interruption, not queue backpressure.

The stale drain at `load.rs:2753-2772` skips only consecutive queued **Tick** commands. It stops on the first other command and preserves it in `pending`. A normal backlog `Snapshot(A), Tick(A), Snapshot(B), Tick(B)` is therefore not equivalent to a latest-state mailbox. Every intervening snapshot is materialized. Settings, Loadouts, Pause, Resume, Probe and Stop are ordering barriers too. Paused ticks take the existing early `continue`; do not invent Completed messages for them in an optimization.

A capacity-two return pool bounds only reusable free storage. It does NOT bound outstanding packets, channel messages, script-held JS values, or work. Preserving nonblocking publication, arbitrary lag, and every accepted event while imposing a hard finite queue bound cannot all be guaranteed simultaneously. A full-queue policy is a genuine behavior/scope decision, not an allocator implementation detail.

## Recommended design in executable-sized stages

### B1 — consumed packet return, no encoding or scheduling change

Add an internal destination-buffer encoding path beside existing public `Vec` APIs. The slot takes a previously consumed `Vec`, clears its length, and copies `finished_data` into it; if none is available or it must grow, allocate normally. Public one-shot APIs and previously returned packet lifetime stay unchanged. Reuse does not eliminate the byte copy; it eliminates repeated output allocation/growth under reuse conditions.

Return the packet only after `SnapshotReader` and `materialize_snapshot` have finished and all Rust borrowed readers have gone out of scope. JS has copied primitive/string/array content by then. Do not wait for Tick or V8 GC: there is no V8 packet view to protect. On malformed input or materialization error, finish the current error handling and return/drop storage through the same ownership guard. Do not change partial materialization/error semantics while implementing reuse.

Use a dedicated invocation-local, nonblocking return channel with capacity two and a host free-list whose **combined free-buffer count** is at most two. Drain returns before encoding; accept only remaining free credits, drop excess. Do not put returns among `ThreadMsg` items: changing when `pump_logs` observes them should not become a hidden delivery dependency. Store the pool inside the started Load instance (or explicitly tie it to that instance); no global pool and no uid-only recycling after restart. Failed send, normal Stop, runtime failure and detached old thread must drop or return only to the old pool. No waiting for a free packet and no queue coalescing.

Capacity retention policy is part of the implementation specification: start with one retained buffer; permit a second only after overlapping use is observed. Reject returns larger than a documented per-buffer cap selected from the deterministic packet-size fixture and later reviewed native size distribution. This report deliberately does not invent a numeric cap from absent packet-size evidence. Oversize packets still deliver, then drop normally. Bound the total free bytes as well as the free count. The cap affects reuse, never admissible message size or script behavior. If free-byte growth exceeds demonstrated live-owner benefit, keep one or disable pooling; do not call it an RSS win.

Observable oracle: the exact same bytes enter the existing FIFO at the same event boundaries. Only allocation identity after consumption may differ. Counter oracle: created, reused, grown, returned, discarded; queued/materializing/free capacity separately; conservation at Stop. A pointer recycled before consumption is a correctness failure even if its current contents happen to match.

### B2 — stream borrowed rows through the bridge

At `with_script_snapshot_input`, replace only the internal action-list projection with a view over existing optional action strings, preserving `filter_map` ordering and its treatment of empty strings. Do not conflate that projection with shim `presentOps`, which additionally filters hidden/falsey actions. Keep existing public `SnapshotInput` callers source-compatible via an adapter; a new internal iterator/view seam can be generic over public inputs and host projection rather than changing public field types opportunistically.

Then use length-plus-iterator reader accessors internally for materialization, preserving public `Vec` getters. Build V8 arrays directly from the verified FlatBuffer vector. Remove nested temporary reader collections as well (for example `make_product_array:2333-2334` calls `buttons()` twice). Keep V8 property insertion order, null/empty defaults, new-array/new-row behavior and exception handling. This does not add lazy proxies or expose Rust storage to JS.

Start with scene entities and their actions, the measured fingerprint-heavy family, then inventory/bank rows only if the same tests and counters show benefit. The reachable/adjacent flood and distance computation remain at the existing observation boundary. Avoid a generation-only cache: loc distance depends on player context and reachability on collision/origin; unchanged entity content does not establish unchanged derived values. Reusing a proven immutable publication family later can remove this projection work, but simply retaining another projection cache now adds an owner.

### B3 — conditional retained-baseline redesign, not bundled with B1/B2

If retained transport ownership is still material after B1/B2, test a **compact immutable per-field baseline** for the scene family. Store ordered scalar records plus a contiguous UTF-8/action table, with explicit null tags and offsets; compare borrowed current input against those values exactly. Do not use probabilistic hashes as equality. Leave other families and public `SnapshotFingerprint` APIs intact at first. `SlotScript::memory_progress` also reads fingerprint inventory/bank state and must retain equivalent diagnostic values.

Two implementations must be distinguished:

1. Compact baseline only, still writing legacy FlatBuffers. This can reduce pointer/header/allocator overhead in nested owned fingerprints but retains both baseline and encoder scratch. It does not remove serialization copies.
2. Compact immutable field blocks also used by an internal message envelope. Snapshot carries tick, mandatory hold, explicit present-field mask and references to changed blocks; unchanged blocks remain on the host baseline, changed blocks survive in queued messages until materialized. This can replace nested baseline storage and avoid copying the same encoded payload into both scratch and posts. V8 materialization remains eager with identical row/array replacement behavior. Versioned internal envelopes and all consumers need an audit; preserve legacy public FlatBuffer APIs and exact-byte tests, and add cross-encoding value/action/lifetime oracles rather than deleting the old ones.

Choose option 1 only if its measured net capacity reduction warrants maintaining a second representation. Choose option 2 only after root explicitly approves the private-wire boundary and its replacement oracle. Do not retain both complete baselines in production. Retaining one whole old `GameSnapshot` instead is rejected: it can pin unrelated widgets/scene families and history. An immutable family already shared with the correct host observation could replace the baseline cheaply, but only with exact derived context and bounded old-version ownership; this is an interface to a publication redesign, not permission to assume it exists.

For either option, changed versions queued faster than consumed still accumulate. Block reference counting does not make that storage disappear. Banks remain forced on NavWorld identity change even if content is equal; hold remains mandatory; absent, empty and default distinctions must be preserved. No cross-client semantic state sharing and no mutation of an old published block.

## Honest improvement envelope

The measured archival `targeted-allocation-owners.md:83-96` active N32 IsolateBuf stack group is 32,127,248 bytes, with fingerprint 14,262,848 and SceneEntityFp 13,628,880 **nested inside it**. At equal per-slot occupancy, a simple N16 scale illustration is 15.3195 MiB for the entire stack group, 6.8011 MiB fingerprint, 6.4988 MiB scene fingerprint. These are not current N16 observations or additive savings. The capture predates borrowed compare and other fixes; the current candidate removes reconstruction churn but not its retained baseline.

`incremental-owner-attribution-report.md:15-32` measured N1/N16 V8 non-mmap stack allocations 1.251/16.997 MiB, a descriptive increment about 1.0498 MiB. That is neither all V8 residency nor pure transport data. VM reservations were explicitly excluded. Widget/Loc snapshots total 53.878 + 28.594 MiB at N16 in that older capture, but B1/B2 do not remove their owners and cannot claim those bytes. Appearance/animation changes since that capture must not be counted again.

Minimum credible gains and ceilings by stage:

- B1: after warmup with equal-size posts and completed returns available, remove one fresh output allocation per successful reuse; still copy exactly packet length L. With K eligible posts and A initial/growth/miss allocations, the allocation-count reduction is K−A. Without reuse, lower bound is zero. Net resident saving has no positive floor; free capacity can increase RSS. At most the eligible fresh packet allocation traffic is removed, not the builder or V8 graph.
- B2: remove copied action-string bytes and temporary reader-vector capacity for the fields traversed, minus any new iterator/adapter bookkeeping. Those objects are temporary, so this is an allocation-traffic/CPU opportunity, not removal of one full retained snapshot. Upper work bound is the existing projection and reader-collection work, not whole-process CPU. No time profile here supports converting it to 0.2296 core.
- B3: net retained allocation reduction = removed fingerprint/scratch/post duplication minus compact blocks, indices, reference counts, queued old versions and retained free capacity. Scene-only removal cannot exceed the old measured scene fingerprint family (6.4988 MiB in the explicitly hypothetical N16 scaling) before replacement costs; zero RSS saving remains credible. Even deleting the entire old IsolateBuf family at that scale would be far short of the Linux 98.68 MiB gap. This is an archival ceiling for that allocation sample, not a universal upper bound on current processes or backlog.

Thus the smallest useful result is concrete allocation removal with byte/lifetime parity, not an invented MiB promise. The meaningful CPU hypothesis is eliminating repeated host projection and transport work across active slots; B1 alone is not the CPU solution. Neither transport alone nor an isolate-pool slogan has measured support for eliminating the approximately 13.57 MiB active-increment gap. Root should combine a successful bridge change with larger measured client/publication/fixed owners, or retain this as a bounded secondary contribution.

## Alternatives rejected and genuine scope choices

- Latest-snapshot mailbox / merge deltas: loses observed intermediate state and potentially chat events, waits and actions; original masks are relative to prior posts, not the last delivered state. Re-keyframing a latest state does not restore those events. Needs a new behavioral policy, not approved here.
- Blocking bounded send: transfers script lag into the client pump and threatens 20ms progression. Arbitrary queue overflow failure likewise adds a new script error. Neither is a hidden implementation choice.
- Recycle at send, enqueue, tick dispatch or Completed: first three are too early; Completed is not a precise snapshot-consumption receipt and can be skipped/absent. Return after materialization instead.
- Transfer builder backing immediately: potentially removes L-byte copy, but packets then retain full builder capacity while the producer needs another builder. Check pinned flatbuffers API and ownership/reset invariants in a future bounded spike; do not assume `collapse()` alone proves efficient reuse. B1 is easier to discriminate and retains exact wire bytes.
- External ArrayBuffer/shared-memory or lazy Rust-backed entity getters: would extend packet lifetime into arbitrary JS retention and alter mutability/property/error/identity timing. Unnecessary for the identified temporary vectors; not recommended while retaining the adapter unchanged.
- Reuse/mutate V8 row objects: retained adapter values may alias `actions` (`shim/_kernel.js:39-47`). Old rows must not change underneath a retained observation; freezing formerly mutable values also changes behavior. Keep current replacement semantics, including the fact that the host root snapshot object itself is a live merged object, not a deep immutable snapshot promise.
- One V8 isolate for many bots: independent module/global state, termination, async waits and errors are isolation boundaries; 256MiB-style VM mappings are not resident targets. No measured evidence justifies a foreign-runtime-like scheduler to recover them.
- Force GC, reduce timeouts or suppress paint/observations: shifts pauses or changes behavior rather than deleting an owner; no authorization.

Root decisions are B3's encoding/contract boundary and any future overload policy. Pool cap selection from packet evidence, iterator types, return-channel plumbing and drop guards are bounded implementation details, provided they cannot affect delivery. The maintained compatibility surface and client fence are not up for replacement.
