# Generate the selected game data

> **Audience:** contributors who regenerate the game data that ships in the
> `api` crate. You need the pinned engine and content checkouts for the revisions
> you verify. Revision 377 is selected explicitly; it is not a default.

The one entry point is `tools/game-data/generate.ts`; its verifier can run a
single revision without requiring the other source checkout to be clean.
Every external source root is a required environment variable — an unset
variable fails closed and names itself, with no machine default:

```bash
export GAME_DATA_274_ENGINE=/absolute/path/to/274-engine
export GAME_DATA_274_CONTENT=/absolute/path/to/274-content
export GAME_DATA_289_ENGINE=/absolute/path/to/289-engine
export GAME_DATA_289_CONTENT=/absolute/path/to/289-content
export RS2B0T=/absolute/path/to/rs2b0t
export GAME_DATA_274_SNAPSHOTS=/absolute/path/to/274-snapshots
export GAME_DATA_289_SNAPSHOTS=/absolute/path/to/289-snapshots
```

```bash
cargo build -p nav-bake --bin cache-content-id
bun tools/game-data/generate.test.ts
bun tools/game-data/verify.ts --revision 289
bun tools/game-data/generate.ts --revision 289
```

Both commands accept `--revision 274` too. Without a flag they attempt both
revisions: 289 is required, while unavailable/dirty 274 is reported as
`REFUSED` without hiding 289's result. An explicitly requested revision fails
on refusal. Cross-pin corroboration is reported as unchecked unless both
revisions passed. Regenerating one revision preserves the other manifest row;
it does not claim to repair or verify that row.

### Revision 377

Keep the four historical source-root variables above set: the existing revision
registry reads them when it loads. Add the selected 377 roots and snapshot:

```bash
export GAME_DATA_377_ENGINE=/absolute/path/to/377-engine
export GAME_DATA_377_CONTENT=/absolute/path/to/377-content
export GAME_DATA_377_SNAPSHOTS=/absolute/path/to/377-snapshots
bun tools/game-data/generate.ts --revision 377
bun tools/game-data/verify.ts --revision 377
```

The 377 source pins are engine `bc47497ee8cf6148dbfb7239714ddd5045c40194`
and content `a15d0faa809f5f8455ef43e1ae4edfdd22512bb2`.
Use a members-world decode (`NODE_MEMBERS=true`). Build the server pack with the
selected engine's full build. For Fairy Ring's modified content, that build uses
`BUILD_VERIFY=false`; this does not bypass the generator's input-pin checks.
The client inputs are the published 377 cache, not a newly repacked versionlist.
`cache-content-id` must verify that cache against its complete decoded snapshot.
The generator never invents a snapshot or copies another revision's identity.

The API embeds `377.json` and its `377/{gathering,quests,debug}.json` families.
It requires the exact selected revision, schema, source pins and family digests.
The verifier reruns the 377 extractors into a temporary directory and compares
all four artifacts and the complete manifest row. It does not change the
historical verifier's checks or require byte equality with 289 facts.

The initial nav bake verifies the quest family through the offline upstream
identity seam, before nav/flag hashes exist. Rebind the core and manifest to the
real bake's hashes afterward. Runtime selection still requires the complete
selected pin; an offline bake identity is not a runtime pin.

The 377 core records named `UNKNOWN` gaps in `coverage`. In particular, it does
not inherit the 289 autocast control contract, special-attack arm timing,
Nurmof/essence and flour stand tactics, constrained-clue access annotation, or
server-ordered/NPC-transform proof. Optional families stay absent when their
contract is not derived; the API does not replace them with another revision.
Frozen equipment and bank lists select queries, not numeric 377 facts: resolved
rows must join the selected configs, packs and map placements. Missing matches
remain absent or explicitly missing.

A generated result proves consistency with the selected Fairy Ring scripts.
It does not prove historical RuneScape accuracy.


Input identity covers tracked scripts/packs/maps and engine decoder/limit
sources, plus the ignored generated files pinned by size and SHA-256 in
`tools/game-data/generated-inputs.json`. Those generated-input pins are tied to
the engine/content commits; changing them is a deliberate input-pin change,
not an automatic blessing of local generated bytes. Unknown, missing or edited
ignored inputs refuse. Platform metadata such as `.DS_Store` is not an input.

At the typed-family cutover, `generateSelected` stages families, core and
manifest beside the live revision directory. Nav must bind the emitted quest
digest **and** schema; sources are rechecked before publication. A refused build
removes staging and leaves the previous assets intact. The final manifest's
digest is computed externally, never embedded in its own bytes.

## Server-ordered content contracts

The revision 289 core includes a generated `server_ordered` catalog.
The extractor joins content aliases, decoded interface properties, and the selected engine paths.
It refuses missing or ambiguous aliases, changed controls, and incorrect interface ancestry.
The selected font and message animation must prove one banker player page for `bank_open_deposit`.
If that page is unproved, only this recipe is unavailable.
Unproved revisions do not inherit revision 289 identities.
The complete catalog source digests are in `provenance.server_ordered_inputs`.
This exact read inventory is separate from the shared family, base, and debug input lists.
Changes to server-ordered proof inputs do not change the existing quest or gathering digests.

NPC numeric operations require a complete transform closure.
Static transforms, scripted transforms, temporary types, and reversion all participate in that proof.
For a visible temporary type, the closure first includes its possible base types.
It then follows all forward transforms from those types.
An unresolved dynamic transform cannot authorize an NPC operation.
Each action compares the ordered OPNPC/APNPC handler pair, with type, category, then global resolution.
The `_` script subject selects the global handler.
A bare subject selects an NPC type, even when a category has the same name.
Only an underscore prefix selects a category, for example `_saltfish`.
The runtime catalog contains only positive operation rows and a complete-evidence SHA-256 digest.
Generation writes accepted and refused evidence to `tools/game-data/evidence/289-npc-transforms.json`. Git ignores this reproducible development output.
Run `bun tools/game-data/generate.ts --revision 289` to regenerate the evidence file and the revision 289 catalog.
The verifier reads a local evidence file when one exists and checks its SHA-256 against `server_ordered.npc_transforms.evidence_sha256`.
If no local evidence file exists, the verifier writes freshly generated evidence to a temporary location and checks its SHA-256. A missing local file is not an error.
A stale local evidence file fails the digest check.
This development-only output is not shipped or loaded by the product.
Unknown label callers and unsupported NPC parameters remain conservative analysis limits, not proved dynamic content.

The API retains one immutable catalog with the selected game data.
Its accessor requires the exact selected pin.
Private decoders construct the inner facts. Public accessors borrow them without exposing constructors or `Deserialize`.
Recipe budgets, deadlines, and recovery limits are reviewed host policy.
Each predicate, outcome, cleanup condition, and predecessor has an explicit `basis`.
`checked` identifies a declaration that the generator checks against selected source.
`host-policy` identifies a host requirement or an unproved engine assumption.
Host-policy conditions do not assert engine behaviour, even when their names describe engine checks.
The inventory-reference, location, held-use, and appearance-handler assumptions remain unproved policy.
Existing source guards still check the content paths, count resume, and modal cleanup.
Each checked condition and predecessor cites the source spans for its check.
`synchronous` means only a checked synchronous server path.
Host-order edges have `basis: "host-policy"` and `synchronous: false`.
This includes the banker pause-resume edge, whose engine handler is not checked.
Loading these facts does not change existing interaction producers or send packets.

Run the extractor tests with the generation checks:

```bash
bun tools/game-data/server-ordered.test.ts
bun tools/game-data/npc-transforms.test.ts
```
