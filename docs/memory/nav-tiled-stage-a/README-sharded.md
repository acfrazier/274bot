# Singleton-warmed Stage A tooling (version 1)

This is a new temporal experiment, not recovery of the original failed all-row
process. It keeps three distinct original calls, one warmup per lane and eight
timed sweeps within each row. It does not preserve global all-row warmup/cache/
allocator history. Only root may accept that experimental change or release any
real phase. No real phase is authorized by this document or generated evidence.

## Entry points and schema

Keep the existing `stage_a.py real` interface and its authorizations unchanged.
New entry point:

    python3 docs/memory/nav-tiled-stage-a/sharded.py --run ABSOLUTE_RUN \
      --authorization PHASE.json --authorization-sha256 EXTERNALLY_FROZEN_SHA

`--standin` is exclusively for inputs immediately under that admitted run's
`fixtures/`, with the original generated byte/dimension caps. It cannot read an
external pack or emit a real comparison scope. There is no retry/resume command.

The protocol version is `stage-a-singleton-v1`. Probe summaries add
`raw_schema=stage-a-raw-v1`, `raw_order=sweep-row-lane/8/3`, and the integer
`raw_elapsed_ns` array. Its index is implicit `(sweep, local row, lane)`; the
root-bound ordinal manifest maps each singleton's local row to its original
1-based ordinal. Repeated identical selector tuples retain separate ordinals.
The ordinary aggregate and all original phase records remain present.

`contract(normalized_rows(full_tsv))` is the exact schema/order/resource/tool
contract. A root F1 authorization has these required fields:

- `schema`, `phase="F1"`, `mode="real"`, `released=true`.
- `run` (absolute admitted build directory), `destination` (new owned release
  directory under that run), and `contract` (exact function output).
- `prerequisites`: the legacy root release prerequisite structure accepted by
  `stage_a.check_release`, including all four new binary/admission hashes,
  generated clean/counting qualification, original tool/manifest/hardware/order,
  Linux guard evidence, correctness release and original full input/TSV bindings.
  The legacy twelve-arm `order` in this nested object is only an inherited
  prerequisite: the new root contract separately fixes the singleton schedule.
- `scheduler_qualification`: `{path,sha256}` reference to the new native
  `qualify_sharded.py` result. Its guard outputs/receipt and actual four-child
  generated smoke are revalidated, not merely its boolean.
- `preflight`: root `{path,sha256}` reference containing `timestamp` (Unix
  seconds), `hardware` from `stage_a.hardware()`, `boot_id`,
  `no_competing_work=true`, `idle_percent>=90`, `steal_percent=0`.

F2 and acceptance require fresh, separately root-issued phase authorizations:
`schema`, `phase`, `mode`, `released=true`, `root={path,sha256}` pointing to the
ORIGINAL F1 authorization, `parent={path,sha256}` pointing to the immediately
preceding complete result, `review_approved=true`, and a fresh `preflight`.
Acceptance additionally requires `method_accepted=true`. Do not copy diagnostic
samples into acceptance. Partial receipts, incomplete ancestor chains, changed
original files, negative/reset budgets and failed/reserved checkpoints reject.
The external authorization hash is mandatory, even when a file is self-consistent.

A native preflight must be at most five minutes old on entry. During the bounded
phase, its original hash and boot/hardware remain fixed; live memory, swap,
50-ms CPU idle/steal and competing executable checks repeat outside child timing.
The preflight's maximum ongoing age is three hours, not permission for a long
run. Available memory must be at least 512 MiB and no swap may be in use.
Fresh preflight is required for every continuation; waiting time is not measured.
This path has not been exercised on Linux by this implementation task.

## Resource accounting and failure records

- F1: rows 1/2, odd/even AB/BA, four children, 480 wall / 360 CPU seconds.
- F1+F2: all 59 ordinal pairs, 118 children, 1800 wall / 1500 CPU seconds.
- Acceptance: pair-major six complete AB/BA replicates, 708 NEW children,
  7200 wall / 6000 CPU seconds; total campaign 9000 wall / 7500 CPU seconds.
- Every child: existing 120 wall / 90 CPU / 1 GiB sampled group RSS /
  4 GiB native hard AS / 256 KiB combined output and file cap.
- Stop on any failure or completed child above 80 wall / 60 CPU seconds.
  Full F2 projection must satisfy both `7.5 * diagnostic_cost <= acceptance_cap`.

The phase directory is claimed before source/input setup, preventing a fresh
budget after interrupted setup. An incomplete claim is not resumable. Each child
reserves its full wall/CPU allowance in a constant-size fsynced checkpoint before
launch. Only validated completion refunds the reservation. Unknown child CPU
adds the full 90-second allowance and stops; measured CPU is not subtracted from
that conservative charge. `RUSAGE_SELF` plus waited `RUSAGE_CHILDREN` includes
Python supervision and `ps` helpers; per-child CPU is a conservative waited-child
CPU delta including its sampling helpers. Probe processes are frozen non-forking
executables. The supervisor CPU alarm reserves all 90 child seconds separately
and leaves two additional seconds for sampling/reaping before admitting a child.

A monotonic wall alarm covers setup, hashing, launches and aggregation. It raises
through the existing bounded runner's cleanup/finally path, killing the owned
group and waiting for its leader; SIGTERM/SIGHUP use that same cleanup path.
A CPU profiling timer is armed before authorization parsing. Bootstrap is bounded
by the smallest phase ceilings; only small hash-bound root/parent receipts and
the non-restartable claim precede cumulative budget admission. Before source,
input, native qualification or contract setup, both alarms use the carried prior
budget plus all elapsed bootstrap work, not a fresh continuation allowance. An
already exhausted budget refuses heavy setup. CPU is tightened after each waited
child. Uncatchable supervisor SIGKILL cannot run Python cleanup: its durable claim
still forbids automatic restart, and root must inspect any remaining owned work.

`claim.json`, one `*.record.json` per completed child, constant-size
`checkpoint.json`, and one final result index replace repeated full-history
progress writes. Final publication conservatively prepays one wall second and
0.1 CPU seconds; exceeding that tail invalidates the result. Separate accounting
fields disclose supervisor, waited-child, unknown and prepaid costs.
`status=complete` means a complete measurement record, NOT accepted performance.
Raw output remains authoritative. Incomplete pairs and failed children remain on
disk. A sixth-pair row peak failure stops immediately before the next row;
pooled CPU/p99 decisions require all six complete replicates. No outlier deletion.

## Storage

One read-only FULL input copy is created in the shared release root during F1;
F2 and acceptance reuse that same copy. The original input is rehashed as well
as the copy before/after launches and at final aggregation. There are 59 compact
selector files, not 708 full pack copies. The root contract binds every ordinal
and normalized shard hash to the original complete TSV.

The whole release directory has a conservative 512 MiB cap, including input,
selectors, child stdout/stderr/receipts, record files, checkpoints, failures and
final JSON. At least 1 GiB free disk plus the remaining declared release capacity
must be available. Each launch additionally reserves 1 MiB of artifact headroom.
JSON is capped at 256 KiB; per-child record/checkpoint/claim files at 16 KiB.
No evidence is automatically deleted. Static build/qualification artifacts are
separate tooling costs, not hidden inside that measurement-storage allowance.
The final full-matrix fixture verifies only one `input.bin` exists.

Writes/storage are linear in child count. Rehashing prior evidence before each
launch intentionally does additional read work; all of that supervision enters
the global budget and F2 projection. It cannot create unaccounted free CPU.
Root owns any remote archive/offload after independent readback.

## Bounded local qualification

Materialize/build new frozen arms using the existing `stage_a.py prepare/build`
commands, never moving path-dependency bytes. Run existing `guards`, both
`generated` variants and `test_stage_a.py --run RUN`. Then:

    python3 docs/memory/nav-tiled-stage-a/qualify_sharded.py ABSOLUTE_RUN \
      singleton-qualification-03

Choose a NEW numbered destination; an existing one is refused. This runs the new
unit/guard suites through the shared runner under 360 wall / 300 CPU / 512 MiB
RSS / 4 GiB AS / 1 MiB output limits. The 826-slot F1/F2/acceptance test uses
explicit deterministic mocked child output, not repeated expensive routing.
It then runs four actual new-probe children on a tiny generated pack and checks
12 old/new clean/counting fixture comparisons and unchanged timing/helper spans.
The comparison requires preserved `run-05` fixture outputs and Git ancestor
`f24de7c`; root must stage that evidence for native qualification, not replace it.
Tests print retained fixture locations. Actual native hard-AS evidence remains
mandatory; a macOS success reports `native_hard_as_qualified=false`.
