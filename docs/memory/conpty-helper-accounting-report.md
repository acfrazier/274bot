# Managed ConPTY helper accounting

This change binds Windows ConPTY helper accounting to the managed launcher. `run_diagnostic.py` takes a bounded Toolhelp snapshot of the explicit launcher PID, selects direct `conhost.exe` children other than the known frontend PID, and records each helper PID and Windows creation-filetime identity in the launcher metadata. The managed runner validates the handoff, rechecks the helper parent and start identity, then adds the helper as an explicit collector role. Receipts preserve those identities in `sampler_result.conpty_helpers` and `role_identities`.

The path fails closed when the helper handoff is missing, no direct `conhost.exe` helper is discoverable, the parent changes, the image is not `conhost.exe`, or the sampled creation identity differs (including PID reuse). ConPTY waits for the identity-bound metadata before starting the collector; Windows panel/headless paths do not require a helper handoff. Unix starts its collector immediately after launcher ownership and does not add helper roles. This is bounded direct-child accounting; it is not arbitrary descendant-tree discovery or a claim that all host helpers are covered.

Verification on macOS: 105 focused unit tests passed across managed runner, ConPTY contracts, process accounting, resource binding, and explicit Windows child discovery. The tests cover missing handoff, successful PID/start-identity inclusion, parent/identity mismatch, non-ConPTY helper gating, empty discovery fail-closed behavior, direct-child image filtering, and preserved Unix collector ordering. No native Windows rerun was performed in this task; the real Windows ConPTY proof remains an orchestrator-run requirement.
